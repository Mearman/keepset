# Contributing

`pnpm install` sets up the git hooks (`prepare: husky`). From then on:

- **Pre-commit** lints and fixes staged TypeScript (`lint-staged`).
- **commit-msg** checks the message against [Conventional Commits](https://www.conventionalcommits.org/) with commitlint, whose type list `release.config.ts` also owns. Describe the code change in the subject, not the review that prompted it.
- **Pre-push** runs typecheck, tests and the build, so a push that CI would reject fails locally first.

## Before opening a PR

`pnpm run prepublishOnly` runs the gate CI enforces: lint, build, typecheck, tests, `publint` and `attw --pack --profile esm-only`. Build before lint's type-aware pass and typecheck: both read the built `dist` and the generated schema. CI also packs the tarball and installs it into a clean project on each supported Node line, runs the CLI from it and builds the site, which is the check that the exports map and the bin work for a consumer. A Browser job runs the built site in Chromium (`pnpm run test:e2e`, with Playwright's browser installed once by `pnpm exec playwright install chromium`), answering every request to another origin from the test itself, so the preview, the listing and the lazy chunks are checked where a missing Node global or a blocked cross-origin read would show.

## Adding an entry

An entry is one JSON document in `catalogue/entries/<id>.json` and, where the crosswalk is not inline, a crosswalk file in `catalogue/crosswalks/<category>/`. Write the entry against the Zod schemas in `src/entry.ts` (the generated `schemas/entry.schema.json` documents the same shape), then check it three ways before committing: `npx keepset validate <id>` for the schema and the crosswalk, `npx keepset fetch <id>` into a scratch file for the recipe, and `npx keepset roundtrip <id>` for the crosswalk's inverse, which also prints the counts and warnings `fetch` would, from the same download. Give an entry the `subjects` it is relevant to as lowercase slugs (the survey import files every operations research item under `operations-research`), and keep them apart from the domain, which is the topic, and the tags, which are the node fields. Record the licence exactly as the source states it, and a dead source's snapshot date with its URL. Never edit an upstream catalogue source, and never modify a source repository to make an entry work: the recipe adapts to the source, not the reverse. Entry ids are stable across forks, so an id is never renamed once published. An entry may also carry a `namespace` (the collection it comes from, outermost segment first) and `aliases` (other names for it). Each namespace segment is an id, and an alias is an id or ids joined by `/`: a bare alias is a name inside the entry's own namespace, and an alias that is a path is a name of its own that files the entry in the group its leading segments name. Every fully qualified name (the whole path of an id or alias) must identify one entry and must not be another entry's id, and an entry's own id and aliases must not give the same fully qualified name twice. The manifest's `namespaceAliases` gives a namespace segment other names; a segment named there must be some entry's segment, and an alias must not itself be one. The catalogue refuses each of these when it is built.

## Graph sources

A `graph/v1` entry's file is read by the parser for its format into a native graph, `{ nodes, edges }`. The topology parsers put nothing on a node but its id, so the shared `crosswalks/graph-v1/topology.json` crosswalk serves them all: `edge-list` (a delimited list, with its delimiter, header lines, comment prefixes and endpoint columns stated, and optionally either `where` conditions a line must meet to be an edge, each a column whose trimmed field equals a value, for a file whose rows are of several kinds, or, for a table that lists several relations or counted pairs such as a connectome's synapse sheet, `keep`, a column and the values whose lines it reads, `multiplicityColumn`, a column holding how many edges a line stands for, a zero standing for none, and `mirrored`, for a table that lists each undirected edge from both ends, which emits each pair once in the direction it is first listed and refuses a line whose mirror never appears, since graph/v1 records direction in its meta and never by duplicating edges), `matrix-market`, `gml`, `pajek`, `ucinet-dl`, `gd-contest`, `witvliet-synapses` and `ogb`. An edge list is read line by line from text decoded in pieces, so a file longer than the engine's longest string is read too. A Witvliet synapse file (`witvliet-synapses`, the `DatasetN_synapses.json` files of github.com/dwitvliet/nature2021) is a JSON array of polyadic chemical synapses, and each partner a synapse faces is one edge from the presynaptic neuron. A UCINet DL file (`ucinet-dl`) is read in its full matrix layout, the one every DL file in the catalogue uses: its nodes are named by its row and column labels (numbered when it has none, and a two-mode file's rows come before its columns), every non-zero cell of the matrix the recipe's `matrix` names (by its position among the file's `NM`) is one edge from its row to its column, and any other layout, an absent diagonal or labels embedded in the data are refused. A Graph Drawing contest file (`gd-contest`, the GD 2004 `.gd4` format) gives nodes `0` to `N - 1` and an edge per vertex pair, and drops the coordinates, which the contest set as random starting positions. Weights, times, node and edge types and splits are carried only by the parsers whose formats state them (below), and node labels beyond ids, attributes and positions by none in this version. A member that is an archive in its turn (the GD 2004 bundle ships its problems in `GD04/challenge.zip` inside `gd04.zip`) is read with an `inner` archive on the recipe's archive, which unpacks the selected member again. An Open Graph Benchmark dataset (`ogb`) is spread over several files of its zip, so its recipe's archive selects them with `files` (gunzipping each with an `inner` gzip) and the parser reads them together, as OGB's own raw readers do: a dataset with one node type has nodes `0` to `N - 1` from `raw/num-node-list.csv.gz` and the pairs of `raw/edge.csv.gz`, and a heterogeneous one has nodes `<type>:<index>` for every type `raw/num-node-dict.csv.gz` counts and the pairs of each `raw/relations/<head>___<relation>___<tail>/edge.csv.gz` its triplet list names, types and triplets in sorted order, each edge file checked against its `num-edge-list.csv.gz`. Only a multi-file parser takes a `files` archive, and it takes no other. A new graph format gets a parser in `src/parsers` that emits the native topology, a variant of the recipe's parser schema in `src/entry.ts`, a branch in `src/parsers/parse-native.ts`, and the graph import's mapping from the source catalogue's format name in `scripts/seed/convert.ts`; a download whose bytes are not in the format the source catalogue records is named in that file's `MISRECORDED_DOWNLOADS` with what it holds, and its entry keeps that as the reason it is not fetchable. A dataset whose pipeline parser is chosen by the dataset's id and not its format (the WormAtlas and WormWiring connectomes, whose one sheet gives several graphs by synapse type) has its recipe written out in `DATASET_RECIPES` in `scripts/seed/dataset-recipes.ts`, with the counts that recipe reads where they differ from the catalogue's and a flag saying where its reading differs from the pipeline's, or the reason no single download gives it. A download whose host a verifying TLS client cannot reach although it still serves the file (a host that sends its certificate without the intermediate that issued it) is named in `UNVERIFIABLE_DOWNLOADS` in the same module with the Wayback snapshot holding the same bytes, and its source is recorded as dead and pinned to that snapshot. A catalogue format that names one publisher's fixed layout (SNAP signed networks, STRING links, BioGRID organism archives, OGB zips) has its whole recipe in `FORMAT_RECIPES` in `scripts/seed/graph-recipes.ts`, a download whose layout the catalogue does not record but which was read has its recipe in `READ_DOWNLOADS`, a download that answers 404 has the publisher's own URL for the same file added beside it by `REPLACED_DOWNLOADS`, and a format read and found to have no form keepset can read (a pickled PyTorch file that only a Python runtime can load, raw tables a graph is built from by other code, a single file too large to hold in memory) has what it holds in `UNREADABLE_FORMATS`, which becomes its entry's reason.

## Table sources

An entry whose source is a CSV or other delimited table uses the `csv-table` parser, which reads the header and rows into `{ nodes }`. A column is named by its header with every run of characters other than letters, digits and underscore replaced by one underscore (`Date received` is `Date_received`; a header cell with nothing left, such as an unnamed index column, is `column_` and its position), the recipe's `idColumn` supplies each row's id (the row number when it is null) and is then not also a column, `id` being reserved for the row's id so any other column of that name is `column_` and its position, and an empty cell is `null` in every row because a crosswalk rule fails on a path missing from any row. A source that writes a missing value as text (`NA`) lists it in the recipe's `nullValues`, and such a cell is null in every column, numeric or not. List a column as numeric with a `factor` to read it as a number and scale it into the target's unit (minutes to seconds is a factor of 60); unit scaling happens there because crossmap's `scale` and `format` refuse `null`. A value the source does not state but a rule gives (the address of a record's file, built from its id) is a derived column: the recipe's `derivedColumns` lists each as a `name` and a `template` of text with `{column}` placeholders, each replaced by that header column's cell as the file writes it (trimmed, unscaled, not encoded, the id column included), so the row gains the column and a crosswalk maps it like any other. A placeholder must name a column of the header (a template naming none, or a stray brace, is refused when the entry is parsed, and a column the header lacks when the file is read), the name must not be a header column's or `id`, and the value is null in a row where a column the template names is empty. A column only some records can have takes a `when` of a `column` and the one value it `equals` for the row to have a value (the address of a file that only one kind of record has), and is null in every other row. A derived column is kept whatever `columns` lists, and may be built from columns that list leaves out. The recipe's `columns` lists the columns the parser keeps in each row (besides the id), so a wide table is not held cell for cell and what an entry carries is written down in the recipe; the file is decoded and read a piece at a time, so a table is bounded by its kept cells and its bytes, not by the length of one string. The crosswalk then moves each kept column onto the field the target has for it with `move` rules, and the round trip holds. Map only what the target needs: a table with personal data keeps its personal columns out of the result by not mapping them.

## Archives and graph file formats

A recipe's `archive` says how the downloaded bytes become the file the parser reads: `none`, a compressed file (`gzip` or `bzip2`), a tar archive (`tar`, `tar.gz` or `tar.bz2`), a zip archive or a 7z archive (`7z`), from which `member` selects the one file to read (or `members` the files of a collection, or `parts` the named files one document is read from), or an Excel workbook (`xlsx`). A `parts` archive names each part and the one member it is read from, and the parser reads the parts together in the order given; only the parsers that read several files take one (`kg-triples`, whose part names are the splits, and `hgb`, whose parts are `nodes` and `links`), and the entry schema refuses it for any other. A bzip2 file is decoded with every block's CRC and the stream's checked; concatenated streams are read as one file, as `bzip2 -d` reads them, and input that ends inside a stream or holds anything after the last one fails the extract step rather than yielding a prefix of the file. A tar archive (plain, gzip or bzip2) is decompressed and scanned in one pass as it is read back from the kept download, keeping the data of only the members its selector can match, and a zip is read by the ranges its central directory names, so an archive far larger than memory is read in the memory of the members a recipe selects; a tar that ends part of the way through a header, a member or its padding fails the extract step. The readers take a source of bytes (`src/source-bytes.ts`) that the fetch's store keeps: Node's `fileStore` (a temporary file, hashed as it arrives, or ranged requests for a zip of at least `RANGED_MIN_BYTES`) or the browser's in-memory store. A change to a reader is tested against the whole-archive reference (decompress into one array, scan that) with the source cut into chunks of several sizes (`src/archive-streamed.unit.test.ts`), and `src/node/large-source.unit.test.ts` checks that a fetch of a source several times its memory budget retains less than the budget, measured after forced collections as the source is pulled. A 7z archive, solid or not, is read by the platform's 7z reader, a port (`SevenZipPort` in `src/archive.ts`) the fetch is given beside its store: Node's (`src/node/seven-zip.ts`) runs 7-Zip compiled to WebAssembly (the `7z-wasm` package) in a worker thread on the file the store keeps, which 7-Zip reads through Emscripten's NODEFS rather than into memory, decodes a solid block once from its start holding only its dictionary, and writes only the selected members to a temporary folder, from which each is read back when it is reached; the browser entry point gives no 7z reader and refuses the kind. Its tests build their archives with the same 7-Zip, so no system `7z` is needed, and check it against the naive reference of extracting the whole archive in memory (`src/node/seven-zip.unit.test.ts`), and the large-source test checks that a solid 7z several times the budget is decoded with the process and 7-Zip's own heap each retaining less than it. corpus too large to hold as one document has a `stream` recipe with a `files` archive read by a parser that makes one row of each file (`member-text`): `streamDataset` downloads the source whole, then hands on each file's row as soon as the file is read, inflating a zip member that is a tar in its turn and scanning it as it is read (`streamFiles` in `src/archive.ts`), so the corpus is read in the memory of one file; the files of a tar come in the order the tar holds them, since sorting them would mean holding them all, and `fetchDataset` refuses the recipe.

A ratings file (one rating per line as user, item, rating and time, which is the layout of an Amazon ratings-only file and of each MovieLens release) uses the `user-item-ratings` parser with the recipe stating the delimiter (`comma`, `tab` or `double-colon`), the header lines to skip, what the items are (`movie` or `product`) and the top of the rating scale. It gives a bipartite graph: a user is the node `u:<id>` of type `user` and an item `m:<id>` or `p:<id>` of the item type (so user 1 and movie 1, which a source numbers independently, are two nodes), and each rating is an edge from its user to its item of type `rating`, whose `weight` is the rating over the scale's top and whose `timestamp` is the time field as the file writes it. The entry's `directed` property records whether that direction is meaningful. Its crosswalk is `crosswalks/graph-v1/rated.json`. The file is read a piece of text at a time and each distinct id is held once, so the parser holds the graph it returns and not the text. A fetch holds more than the parser does, because the crosswalk step copies every edge, so a release with more edges than that step can hold is given no recipe, with the failure as its reason, until the step can.

A KONECT download is a bzip2-compressed tar archive of `out.<network>` (the edges), `meta.<network>` and a readme, read with the `konect` parser on the member the pattern `(?:[^/]+/)?out\.[^/]+` selects. The first line of `out.<network>` names the network format and weight type (`% sym posweighted`), an optional second line the edge count and the size of each node set, and each line after them one edge as the source node, the target node, the weight and the time (the KONECT Handbook, section 9.1). The recipe states whether the third column is read as the edge's `weighted` weight and whether the fourth is read as its `timestamped` time, and the parser fails when the recipe disagrees with the file, so a weight or a time the file holds is never dropped silently. A bipartite network numbers its two node sets independently from 1, so its nodes are `l:<n>` and `r:<n>`. The crosswalk is the one that carries what the recipe reads: `topology.json`, `weighted.json`, `timestamped.json` or `weighted-timestamped.json` in `crosswalks/graph-v1/`, since a crossmap rule fails on a path missing from any element and the shape of the native graph therefore has to be stated.

A knowledge graph triples file uses the `kg-triples` parser: one triple per line, with the recipe stating the delimiter (`tab` or `space`), which field is the relation (`head-relation-tail`, or `head-tail-relation` as OpenKE's id files write it), what each file's first line is (`none`, a header of column `names` that is skipped, or the triple `count`, which is checked) and whether every field is `quoted` in double quotes, which are removed. Nodes are the heads and tails in order of first appearance and carry no type, since the files type relations and not entities; each line is an edge from head to tail whose `type` is the relation as written, and a repeated triple is two edges. A download with a file per split is read with a `parts` archive whose part names are the splits (`train`, `valid`, `test`), and each edge's `split` is the part it came from; the crosswalk is `relations-split.json`, and `relations.json` for a single file, whose edges carry no split. The parser holds the graph it returns and not the text, each entity's id once however many triples name it, but a fetch holds more because the crosswalk step copies every edge, so a download with more triples than that step can hold at Node's default heap keeps its layout in the import and is given no recipe, with the failure as its reason.

A Heterogeneous Graph Benchmark download is a zip of the dataset's directory, read with the `hgb` parser from the parts `nodes` (`node.dat`: id, name, type code and, on the node types that have them, attributes) and `links` (`link.dat`: source, target, link type code and weight). The recipe names the node types and, for each link type, its name and the node types it joins, in code order, as the dataset's `info.dat` gives them, since `info.dat` itself is written in more than one form. Nodes are `node.dat`'s lines in file order with their type's name as `type`, edges `link.dat`'s lines with their link type's name as `type`; the parser refuses a type code the recipe does not name, a link whose endpoints are not of the node types its link type joins, and a weight other than 1, the only weight the benchmark's files hold. Names, attributes and the label files are not read. The crosswalk is `typed.json`.

A file of user-item counts (user, item and count per line, the layout of the HetRec 2011 Last.fm `user_artists.dat`) uses the `user-item-counts` parser, with the delimiter, header lines and item type stated: users are `u:<id>` of type `user` and items carry their type's prefix (`a:<id>` for an artist), as the ratings parser numbers its two node sets, and each line is an edge of the item type's edge type (`listened`) whose `weight` is the count. Its crosswalk is `typed-weighted.json`.

## Seed imports

Two imports seed the catalogue from sources kept read-only in `scripts/seed/sources/`: the graph import (`pnpm run seed:import:graph`, reading the thesis pipeline's catalogue) and the operations-research import (`pnpm run seed:import:or`, reading the survey and its curation). Each writes its entries and a report listing every source item once with its outcome, deletes the entries an earlier run wrote that it no longer produces, and never touches another import's entries. `pnpm run seed:check` runs both without writing and fails when a committed entry or report differs from what the inputs produce, so a source or curation change is always committed with the entries it produces.

An entry whose source is a spreadsheet uses a sheet archive kind with the name of the sheet to read: `xlsx` for an Excel workbook, `xls` for a legacy binary Excel 97 to 2003 workbook (BIFF8 in a compound file; an Excel 95 or earlier workbook and an encrypted one are refused) and `ods` for an OpenDocument spreadsheet, whose sheets are its tables. The `csv-table` parser (or `edge-list`, for a graph) reads the CSV the sheet is turned into, which is the same for the same cells in all three: one line for every row number of the sheet up to the last row that holds a value (so `skipLines` is the number of rows above the header as an editor shows them, and the formatted but empty rows after the data are left out), every line as wide as the sheet's widest row, a date cell written as ISO 8601 text (in xlsx and xls it is recognised by its cell style's number format, in either date system; an OpenDocument date carries its own value), a time alone as `hh:mm:ss`, a number as the text the spreadsheet stores (an xls workbook stores a binary double, written as the shortest decimal that is that double), a boolean as TRUE or FALSE, and a formula as its stored result. An OpenDocument cell or row that repeats is written as often as it repeats when it holds a value. A spreadsheet is read whole. A spreadsheet inside a zip or tar is read with a sheet kind as the member's `inner` layout, so a member selected by its extension (a file renamed every quarter) still reads in one recipe. The curation records such an item as a table with an `archive`. A macro-enabled workbook (`.xlsm`) is the same package with its macros stored beside the sheets, which are ignored, so it is read the same way; a workbook inside an archive keepset does not unpack (RAR) is not. A set of instances laid out one per sheet is read as a collection whose archive selects the workbooks with `members` and has `inner` of kind `xlsx`: every sheet of every selected workbook, or every sheet whose whole name the `inner` `sheets` pattern matches, is one instance, read as its CSV by the instance parser at the path `<member>/<sheet>`. A collection whose wanted files sit inside an archive that is itself a member of the download (the transcripts of a corpus shipped as one tarball in another) uses `inner` of a file archive kind with its own `members` selector instead: each matched member is opened as an archive, every file the inner selector matches is one instance at the path `<member>/<file>`, and the outer archive is read once, keeping only the members its selector matches. The `hhcrsp` parser reads such a sheet in the home health care routing layout of labelled blocks side by side (positions, required services and their count, service durations, caregivers' skills and windows, patients' windows), and refuses a sheet whose blocks disagree or hold a value no header labels.

A point shapefile uses the archive kind `shapefile`, whose `member` selects the `.shp` in the zip; the `.dbf`, `.prj` and `.cpg` of the same name beside it are read with it, and the `csv-table` parser reads the CSV they are turned into: the attribute table's field names, then `geometry_x` and `geometry_y` (the coordinates as the shapefile stores them) and `geometry_latitude` and `geometry_longitude` (the position in WGS84 degrees), one line per record. A character field is trimmed, a number is the text the table stores (a field of asterisks, dBASE's overflow, is empty), a date is ISO 8601 and a logical `true` or `false`. The `.prj` must define a geographic system or a Lambert conformal conic projection with two standard parallels, in metres, on a datum that coincides with WGS84 (WGS84, ETRS89 or RGF93), and the `.cpg` must name UTF-8 or ISO-8859-1; any other coordinate system, encoding, shape type or field kept outside the table is refused rather than read approximately.

A Socrata resource (`https://<host>/resource/<id>.csv`) is read with a recipe `paging` of kind `socrata-resource`: the download reads the resource's row count, then pages of `pageSize` rows in the order of the rows' ids, checks that each page holds exactly the rows it should (a response cut short in transit is an error, not a table with rows missing, which one long download of a large table was) and that its header is the first page's, and joins them under the first header into the one CSV the parser reads. An OpenFEMA entity is read the same way with the paging kind `openfema`: the source URL is the entity's (`https://www.fema.gov/api/open/v3/<Entity>`) with the `$select` that names the columns to read, the count comes from the API's own metadata, and the pages are read in the order of the entity's id. A CKAN datastore table is read the same way with the paging kind `ckan-datastore`: the source URL is the table's `/datastore/dump/<resource id>` and the count comes from the portal's own `datastore_search` API. A Socrata `rows.csv` export URL is one file and has no paging. A table is given a recipe only when its kept cells (its rows times the cells each row keeps, its id included) are within what a fetch holds in memory, which is why a recipe lists the `columns` it keeps and the importer refuses a table that would hold more.

An entry whose source is an ArcGIS feature layer uses the `geojson` parser with a recipe `paging` of kind `arcgis-query`: the source URL is the layer's, the download reads the layer's feature count and then its pages in the order of the `orderBy` field until it holds them all (a layer that does not page by offset is an error, not an endless loop), and the pages are joined into one GeoJSON feature collection, which is what the provenance hashes and the parser reads. The parser reads one row per feature, naming a column by the property it comes from; the recipe's `columns` lists the properties kept, `geometry_latitude` and `geometry_longitude` hold a point feature's position (null for any other geometry), a column in `numericColumns` is a number times its factor, a column in `dateColumns` is an epoch-millisecond number written as ISO 8601 text, and any other is text. The curation records such an item with the outcome status `fetchable-arcgis`, the layer's property names as the header and its URL as the download URL.

The operations-research curation (`or-survey-curation.json`) holds one item per surveyed dataset: the entry's id, namespace, name and licence, the download URL, and either a recipe (how to read the table, the file's header cells exactly as it writes them, which columns fill which node fields) or the reason there is none yet. Check a curation with `pnpm exec tsx scripts/seed/or-validate.ts <file>`, which reports every problem at once, and run each fetchable item on a real sample of its download through the fetch flow with `pnpm exec tsx scripts/seed/or-verify.ts <file>` (network): it prints how many rows read and what each mapped field holds, so a mapping onto the wrong column shows as an empty or implausible field. The sample is the start of the file, so a fault further in (a repeated or empty id, a malformed row, a table too large for memory) only shows when the whole download is fetched, which `or-verify.ts <file> <ids> --whole` does and is the last check before a recipe is kept. A table past a row limit is refused a recipe, and personal columns are left out of a mapping. A source that does not change (a file committed to a repository, a published dataset) can record its node count as `expectedNodes`, which the entry carries as `expectedCounts` so a fetch warns when the result differs; an open-data table that grows is left without one.

A seeded entry never gets its licence from a default. The graph import reads `scripts/seed/sources/graph-licences.json`, which holds one record for each publisher (the URL prefixes its downloads live under, and the page that states its terms) and a record for each dataset whose terms differ from its publisher's or whose publisher states them per dataset; a dataset's licence is the record for the source its recipe fetches, and the import fails for a dataset no record covers, for a dataset of a publisher that states terms per dataset where the dataset has no record, and for a record that serves nothing. The operations-research curation records the same thing for each item in its `licence` field. In both, the terms are either stated (the licence as the source writes it, the page or file that states it, and the words that do) or a record that none are stated (every page or file read, and what the reading found), so `unrecorded` always means someone read the source. Where a platform keeps each dataset's licence in a machine-readable record (Socrata, CKAN, ArcGIS Hub, GitHub, Hugging Face, Zenodo), an item recorded as stating none must list that record among the pages it read, and `pnpm run seed:audit:licences` (network) fetches each record and fails when it disagrees with the curation about whether a licence is stated. A licence is recorded as an SPDX id only where the source states one that maps to it exactly; terms with no SPDX id are recorded as a named custom licence with the URL of the terms.

## Source snapshots and liveness

Every source URL an entry records should be pinned to a Wayback Machine snapshot, so a recipe still has its bytes once the host drops them. `pnpm exec tsx scripts/archive-sources.ts` does it: for each URL without a snapshot it takes the one the availability API already holds, requests a new capture with Save Page Now only when there is none, and writes `{ timestamp, url }` on the source in the entry file, changing nothing else in it. A capture, found or newly made, is pinned only after its raw `id_` form has been requested back and answered with the captured bytes rather than the Wayback Machine's own page (a capture can be recorded and never serve its bytes: indexing lags a capture, and a raw form can answer the archive's 404 page for hours after Save Page Now returned); where the live source still answers, the capture's media type, stated length and first bytes are compared with it. A capture that fails the request back is not pinned, is remembered as rejected in `reports/archive-state.json` so the capture index offering it again is not trusted, and a fresh capture is requested in its place. A URL that cannot be archived goes in `scripts/archive-sources.report.json` with a reason (`size-limit`, `excluded`, `access-wall`, `paged-api` or `source-error`) and what was observed, and a pin that served its bytes is recorded there as verified. `pnpm run archive:check` fails when a source has neither a snapshot nor a line in the report, when a pin is not recorded as verified, or when the report lists a source or a verification the catalogue no longer supports. `pnpm exec tsx scripts/archive-sources.ts --verify` requests the raw form of every pin the report does not record as verified, records the ones that serve their bytes and removes the ones that do not from the live sources that hold them, so the next run captures them again; a failing pin on a dead source stays (the entry schema requires it, and the source cannot be captured again) and makes the run exit non-zero, and `--reverify` asks again about the pins already recorded as verified. A failure that says nothing about the URL (a busy service, a timeout) leaves it unresolved for the next run; the run writes the entry files and the report as each URL settles, so it can be stopped and started again, and it keeps the day's capture count in `reports/archive-state.json`.

Save Page Now runs anonymously at its documented limits unless `IA_ACCESS_KEY` and `IA_SECRET_KEY` (an Internet Archive S3-style key pair, from https://archive.org/account/s3.php) are both set, which raises them. A seed import carries over the snapshots its committed entry files pin, so a re-import does not undo an archive run.

`pnpm run sources:check` requests every recorded source politely (HEAD, falling back to a request for the first byte, paced per host with backoff) and writes `reports/source-check.json`; with `--baseline` naming an earlier report it also notes a changed stated length. It edits no entry. The Source liveness workflow runs it on a schedule and opens, updates or closes one tracking issue; marking a gone source `dead` and pinning its snapshot is then a reviewed change.

## Adding a category

A category names a normalisation target. Define the target as a Zod schema in `src/targets/`, register it in the category registry with its id (`<kind>/v<n>`), and name the target's arrays an entry may record counts for. A category is collected for free: a recipe that selects its files with `members` (where a document's recipe selects one with `member`), by path, by the extensions a name ends with, or by a regular expression the whole path matches (the way to leave out a readme or a solution that shares the instances' extension), resolves to `{ meta, instances }` with the schema derived from the category's own. Members are read in path order, each is parsed with the recipe's parser and the crosswalk is applied to each, so one crosswalk serves a format whether it arrives as one file or as a collection. A format that is a list of instances in text gets a parser of its own in `src/parsers` that names the columns it gives each node, which of them are text and the header keys it gives each instance, and is registered in `src/parsers/instance-shapes.ts`, where the seed import checks a curation against it. The category lands with at least one entry that resolves to it, and the site's listing pages pick it up on the next build.

## Constraints a change must preserve

- **The site consumes the package, never a parallel copy.** `site/build.ts` reads the catalogue through the package's own exports, so the site cannot drift from the library.
- **Upstream catalogue sources are read-only.** The PhD pipeline's catalogue and every other upstream source are surveyed, never modified; the seed import emits keepset entries from them.
- **A fetched dataset's licence is its source's**, recorded as the source states it. The catalogue's metadata and recipes are repository content under MIT.
- **Recipes fail loudly.** A recipe that cannot parse, a crosswalk that does not validate and a count that disagrees with the entry's recorded expectation are errors or warnings, never silent adjustments. No fallback parsers, no per-source overrides outside the entry document.
- **Own-property access for data-controlled keys** (see `src/own.ts`): catalogue entries and parsed documents are untrusted input, and `__proto__` never reaches a record write.
- **Generated files are never hand-edited or committed.** `schemas/`, `dist/`, `dist-cli/` and `site-dist/` come from `pnpm build` and are gitignored. Fix the Zod schema or the generator, not the output.
- **No wall-clock figures in tests or docs.** Assert structure and counts of work.

## Releases

A push to `main` runs semantic-release in CI (the `release` job in `ci.yml`, whose filename the npm trusted publisher is registered against). It reads the conventional commits since the last tag, bumps the version, publishes to npm through OIDC trusted publishing with provenance, tags the release, writes `CHANGELOG.md` and commits it back to `main`. Never hand-bump the `package.json` version or edit `CHANGELOG.md`: both are overwritten by the next release. The release job needs a GitHub-hosted runner. `main` is protected by a ruleset that requires a pull request, the `Required Checks` job, resolved review threads and a linear history, and allows only rebase merges, with auto-merge enabled on the repository. The workflow's own token cannot bypass a ruleset, so the release commit and tag are pushed over SSH with a deploy key (the `RELEASE_DEPLOY_KEY` secret holds its private half) that the ruleset lists as its only bypass actor; rotating it means replacing the repository's deploy key and that secret together.
